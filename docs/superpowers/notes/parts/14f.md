# 14f: sync folder — notes

Plan `../../plans/2026-10-12-tasinabilirlik-14f.md`, spec §3.1, §8, decisions 11, 12, 15. Step 14 is complete with this part.

## Follow-ups

- **The shared folder moves at run time**: the store keeps it behind a mutex shared by its clones and the settings writer; setting up or leaving the sync folder needs no restart (files, `set_shared`, the watcher's `follow`, a reload).
- **A typed path instead of a folder picker** for Keep Settings in a Folder, as Export and Import (14d); a cloud folder found by the places is suggested in the description.
- **No clickable Review… in the status bar**: the notice is plain text; it says "Review it in Settings > Sync and Backup", where each copy has a Review… row.
- **Themes are merged key by key too** (the spec only asked for their copies to be recognised), with the same re-check before the write.
- **OneDrive's `settings-<COMPUTER>.toml`** is recognised for the computers in the folder's `machines/` (an empty file per computer, written at setup: no two computers write the same file). A computer renamed after setup is not known by its new name until it sets the folder up again.
- **Only `Value`, `System` and `Local` changes follow settings.local.toml**: a View menu option, pins or the lists always go to the shared file (shortcut: a key also in settings.local.toml keeps winning there).
- **mtime granularity**: two writes of the same size within one timestamp tick (FAT: 2 s) are not told apart; the conflicting-copy review is the net for that.
- **A folder whose parent is also gone** (a USB drive) is not watched; Check Again on its row looks again. Nothing polls.
- **Changes made while the folder is away** are kept in memory (pins stay shown) and written at the first reload that finds it; they are lost if Gezik quits first (the row says how many wait).
- **Templates are never written over** when setting up or leaving the folder (only missing ones are copied), so backups never need them.
- **The 14e `shortcut:` note in `settings_backup.rs` is resolved**: `Folders { shared, local }`; views.toml and `backups/` are this computer's.
- **No new actions**; menu id 2813 (Only on This Computer / Use the Shared Value) in the row menu.
- **Checklist numbers** go on from 14e: macOS 376–378, Linux 273–274.
- **Windows GUI test** not run (no GUI while the user is at the PC).

## Review fixes

The 14f review found four ways to lose data; all fixed:

- **Out-of-order writes**: a change parked after a failed write was written at the next reload, over a newer change made meanwhile. Now, while anything waits, a new change waits behind it, and the waiting ones are written in order by the writer thread.
- **Whole lists from an old copy**: a pin made while the folder was away (on the last copy's `[x]`) was written as `[x, w]`, over another computer's `[x, y, z]`. A waiting change is now kept as the text it was made on and the text with it, and made again on the file as it is (`sync_folder::three_way`): keys we changed take our value where the file still has the old one; lists both changed get our added, removed or moved items (`merge_list`: `[x, y, z, w]`); a key both changed stays as the file has it and our value goes to Gezik's own conflicting copy (`settings (Gezik conflicted copy).toml`) for a Review. The same merge is used when the file changes between the read and the write. Waiting changes are kept in `pending-settings.toml` in the local folder too (a quit while the folder is away loses none) and written at start when the folder is there; while it is away the window shows settings.toml with them.
- **Stop lost this computer's values**: Stop Keeping Settings There now writes settings.local.toml's keys into the copied settings.toml (key by key, comments kept), so the tray, the shortcut and Only on This Computer values stay this computer's.
- **A user's own themes taken for copies**: `Dracula 2.toml`, `Nord (2).toml`. Only a service's mark (`conflicted copy`, `.sync-conflict-`, `_conflict-`, `-<known computer>`, Gezik's own) makes a theme's copy; a numbered name (`(1)`, ` 2`) counts only for settings.toml and only when its contents differ, and Merge never moves such a file to the trash.

## Screen-test fixes

- **[system] from a settings row** (Quick look, Reset to Default) went to the shared file when the key was not in settings.local.toml yet: every `[system]` write now goes to the local file, and setting the folder up leaves this computer's `[system]` out of the copy written there (it is in settings.local.toml).
- **Use the Shared Value** left an empty `[view]` header in settings.local.toml: a table it empties goes.
- **The sync row while the folder is away** says how many changes wait ("Not available — 2 changes wait"), counted each time the rows show.
- **The "not saved yet" status** stays no longer: once nothing waits, a reload clears it in every window and in the settings window.
- **"Slint: long changed callback chain" warnings** (~3,600 in the screen test): not reproduced without the GUI. A watcher test shows one change makes one reload (no reload storm from the parent and local folder watches), and a reload that reads the same files as before no longer applies anything. If the warnings come back, they are a property ping-pong in the window to find with the GUI.
