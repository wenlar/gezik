# 16d: Git status — notes

Plan `../../plans/2026-10-14-gelismis-16d.md`, spec `../../specs/2026-10-13-gelismis-design.md` §8, §14 16d.

## What is in

- **Repository look** (`gezik/src/git.rs` `find_repo`, on the loading thread in `navigation.rs` `list()`): `.git` (a folder, or a file `gitdir: …` for worktrees and submodules; `commondir` followed) in the folder and the folders above, up to the home folder when under it, else to the drive's root. Not on a network drive (`[git] network = false`), not inside a `.git` folder, not with `[git] status = false`. Outside a repository nothing else happens: no thread, no process (test with a counter).
- **Program** (`program`): `[git] program`, else `git` (`git.exe`) in an absolute PATH folder (never the folder shown); on macOS `/usr/bin/git` only if `xcode-select -p` succeeds, then `/opt/homebrew/bin/git`, `/usr/local/bin/git`. Found once per setting, on the first run's thread. None: "Install Git to see repository status" once a run of Gezik.
- **Run** (`status`): on a thread of its own, `ChildProcess::spawn_piped` (16c), stopped by `wait_or_stop` when the pane leaves the folder or closes, a newer run starts, or `[git] timeout` (10 s) passes. First `git config -z --show-scope --name-only --get-regexp '^filter\..*\.(clean|process)$'`, then `git --no-optional-locks -c core.fsmonitor=false -c core.quotepath=off -c protocol.allow=never [-c filter.<repo's own>.clean= -c filter.<…>.process=]… status --porcelain=v2 -z --branch --untracked-files=normal --ignore-submodules=dirty --ignored=matching|no -- .` in the folder shown. Environment: `GIT_TERMINAL_PROMPT=0`, `GIT_NO_LAZY_FETCH=1`, `GIT_OPTIONAL_LOCKS=0`, `LC_ALL=C`, `GIT_DIR`/`GIT_WORK_TREE`/`GIT_INDEX_FILE`/`GIT_OBJECT_DIRECTORY`/`GIT_COMMON_DIR` removed.
- **Marks** (`gezik-core/src/git.rs`): porcelain v2 read (`1`, `2` with its second path, `u`, `?`, `!`, `# branch.*`); `GitMark` (ignored, untracked, added, renamed, staged, modified, staged + modified, conflict); deleted paths go to a count. `folder_marks`: a name's own mark, a folder the most important inside (conflict > modified > staged > added > untracked; ignored inside never counts), the folder shown itself inside an ignored or untracked folder marks every row. Stored per view in `view/folder_git.rs` (`FolderGit`: names with a mark only).
- **Refresh** (`view/folder_git.rs`): a new repository folder runs at once; the same folder listed again (the folder watcher's reload, a pane made active, F5) and any change in `.git` (`HEAD`, `index`, `FETCH_HEAD`, `packed-refs`…, and `refs/` with what is under it; `*.lock`, `objects/`, `logs/` do not count) run after 300 ms; changes during a run make at most one more (`Pacer`, tested). No timer otherwise, no polling. The `.git` watch is made on the run's thread and kept while the same repository shows.
- **UI**: a badge at the icon's bottom left (`file-icon.slint`, list, grid and Miller columns): orange dot modified, green dot staged, half and half both, green `+` added, green `→` renamed, grey ring `?` untracked, red `!` conflict; ignored rows faint as cut ones. Theme keys `git-modified`, `git-staged`, `git-untracked`, `git-conflict` (four built-in themes, `example.toml`). **Git** column (`ColumnKey::Git`, index 11, header menu id 3250, only in a repository), sorted by its header (`SortKey::Git`: conflicts first, unchanged, ignored last). **Group by ▸ Git** (`GroupBy::Git`, id 3251; also the View menu, `[view] group = "git"`). Filter words `git:changed|modified|staged|untracked|conflict|ignored`, `-git:…` (`gezik-core/src/git_filter.rs`; rows pass while a repository's first run goes on). Status bar: a part of its own after the item count, `⎇ main ↑2 ↓1 · 5 changed · 1 deleted`, `⎇ (a1b2c3d)` detached.
- **Settings**: `[git] status, program, ignored, network, timeout` (template, schema for the settings window, parser, `docs/configuration.md`); a change makes every pane read its folder again.
- **Off** inside archives, in search results, the trash and This PC (no repository look there).

## Safety (a hostile repository)

Checked here: in a repository with `core.fsmonitor` and `filter.evil.clean` set to commands writing a marker file and `* filter=evil` in `.git/info/attributes`, a plain `git status` after a file's stat changed runs both (the marker appears). Gezik's run does not (`real_git_marks_a_repository_and_runs_none_of_its_config`).

- `core.fsmonitor=false` always (also a user's own fsmonitor: status is limited to the folder shown and costs little).
- Filter drivers set by the repository's own config (`local`, `worktree` scope, includes there too) get empty `clean` and `process` (empty means none in git's `convert.c`). The user's global or system ones (git-lfs) stay: emptying them would make LFS files look modified.
- `textconv` and `diff.external` are not used by status. Status runs no hooks, and with `--no-optional-locks` writes no index (so no `post-index-change`).
- `protocol.allow=never` and `GIT_NO_LAZY_FETCH=1`: a partial clone's missing object is never fetched (which could run `core.sshCommand`).
- `--ignore-submodules=dirty`: no git runs inside a submodule with its own config; a submodule shows as modified only when its commit differs.
- git is started by its full path; Windows never picks a `git.exe` from the folder shown.
- A repository owned by another user: git's own `safe.directory` check refuses it; its message shows once in the status bar ("Git: detected dubious ownership…"), no marks.

## After the code review and the screen test (PR #147)

- **Config through the environment**: every run's config (`core.fsmonitor=false`, `core.quotepath=off`, `protocol.allow=never`, the emptied filter drivers) goes through `GIT_CONFIG_COUNT`/`GIT_CONFIG_KEY_n`/`GIT_CONFIG_VALUE_n`. `-c filter.x=y.clean=` split at the first `=` and left a driver named `x=y` on (checked with git 2.47: the marker file appeared). A repository driver whose name holds `=` or a line break is refused anyway: no status, git's reason in the status bar. Test with a hostile `x=y` driver.
- **Fails closed**: the filter look accepts only exit 0 or 1 (129: an old git without `--show-scope`, 128: a config git cannot read → no status). **git 2.31 or newer** (`git version`, read once per program; `GIT_CONFIG_COUNT` came in 2.31); older: "Git 2.31 or newer is needed".
- **No transport at all**: `GIT_ALLOW_PROTOCOL=none` (git's own allow list, which no config widens: a repository's `protocol.ext.allow = always` beat `protocol.allow=never`; checked, the `ext::` command ran before). Test with an `ext::` remote. Renames stay on: a missing blob in a partial clone can no longer be fetched (the status then fails rather than fetching).
- **`.git` watch**: events are judged by their path inside the git folder (a repository under a folder named `objects` or `logs` lost every event). Test.
- **Links and junctions**: the folder is canonicalized once in `find_repo` (`\\?\` taken off); the look, git's folder and the prefix use the real path (`Repo::real`). Test with a junction (Windows) or a symlink (Unix).
- **Case and composition**: marks are kept and looked up case-folded on Windows and macOS, NFC on macOS (`icu_normalizer`, already linked by gezik-search). Test.
- **`[git] program`**: a full path, or a bare name looked for on PATH; a relative path is never used. Test.
- **Small reads**: a `.git` file and `commondir` are read only when plain files, at most 4 KB (a FIFO never blocks the loading thread). An empty `.git` folder (no `HEAD`) is no repository; `.GIT` counts as `.git` on Windows and macOS. Tests.
- **git missing** is looked for again after 5 minutes (on the next run) or a settings change.
- **No stale marks**: a run that gives no status (no git, too old, refused, too slow) drops the marks, the Git column and the branch at once, and the folder counts as no repository (Group by Git falls back to no groups; also with `status = false`). Why shows in the status bar's Git part beside the item count, not instead of it.
- **Status bar**: `· 1 conflict` (tn!).
- **Badges**: symbols 11 px at 16 px icons (dots 8 px), white symbols on filled circles with a ring in the list's color; renamed blue (new theme key `git-renamed`), untracked a filled grey (darker in the light themes).
- **Git column** sits right of the name (after Size it touched the right-aligned numbers).
- **Group order**: Conflict, Modified, Staged and modified, Staged, Renamed, Added, Untracked, Unchanged, Ignored.

## Deviations

1. **`refs/` is watched with what is under it** (the spec says non-recursive): a branch moved by a commit lives in `refs/heads/<name>`, a push changes `refs/remotes/…`, two levels down.
2. **No sharing between panes and windows**: each pane runs for its own folder (two panes on the same folder of one repository is rare; each run is limited to its folder anyway).
3. **The status bar's Git part does not open the Git menu, and the deleted files' names are not listed** on a click: both with 16e's Git menu (the count is there).
4. **The timeout note** says "Git status took too long ([git] timeout)" without the `untracked-files=no` hint (there is no such setting; `[git] ignored = false` is the usual help).
5. **Extra safety** beyond the spec (`--ignore-submodules=dirty`, the filter driver pass, `protocol.allow=never`, `GIT_NO_LAZY_FETCH`): a second short `git config` process before each status.
6. **No Sort by ▸ Git menu item**: the column's header sorts (`[view] sort = "git"` and views.toml read it).
7. **No "pending" state**: until the first run of a folder ends rows have no mark (groups and sorts treat them as unchanged; filter words let everything through meanwhile).

## Known limits

- git installed while Gezik runs is found after a restart or a change of `[git] program`.
- A file whose name differs only in case from the index's (Windows, macOS) gets no mark.
- Marks of folders below the one shown come from the same run; a change deep inside a sub-folder that the folder watcher does not see shows at the next `.git` change or reload.
- WSL paths (`\\wsl$`) count as network folders: off by default.
