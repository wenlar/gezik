# Automatic updates on Linux: manual checks

Numbering goes on after `highlight-where-linux.md` (309). Results go to `../linux-test-results.md`. Spec: `../../specs/2026-10-14-guncelleme-design.md`.

**Setup for 310–314** (a local feed; the release build ignores it, so these use the `measure` profile): build this branch twice, once as is and once with the workspace version bumped (`version = "0.1.0-rc.99"` in the root `Cargo.toml`, not committed), with `cargo build --profile measure -p gezik`; keep the first binary as `~/old/gezik`. Make the packages from the second: `mkdir -p /tmp/feed/gezik-0.1.0-rc.99-linux-x64 && cp target/measure/gezik /tmp/feed/gezik-0.1.0-rc.99-linux-x64/ && tar -C /tmp/feed -czf /tmp/feed/gezik-0.1.0-rc.99-linux-x64.tar.gz gezik-0.1.0-rc.99-linux-x64`, and `bash scripts/linux/appimage.sh target/measure/gezik 0.1.0-rc.99 /tmp/feed` for the AppImage. Then `cd /tmp/feed && sha256sum *.tar.gz *.AppImage > SHA256SUMS.txt` and write `/tmp/feed/releases.json`: `[{"tag_name": "v0.1.0-rc.99", "draft": false, "prerelease": true, "html_url": "https://github.com/wenlar/gezik/releases", "assets": [<one {"name", "browser_download_url" (the local path), "size"} per file above, SHA256SUMS.txt too>]}]`. Start with `GEZIK_CONFIG_DIR=/tmp/gezik-cfg GEZIK_UPDATE_FEED=/tmp/feed/releases.json`.

310. **Tarball install.** Run `~/old/gezik` as above: about 10 s after the window opens "Gezik 0.1.0-rc.99 is ready — installs when you close it · Restart now · What's new"; `/tmp/gezik-cfg/update/0.1.0-rc.99/x/gezik-0.1.0-rc.99-linux-x64/gezik` and `ready` exist. Close the window: `~/old/gezik --version` says `gezik 0.1.0-rc.99`, `~/old/gezik.old` is the old one (still executable). Start it again: "Updated to 0.1.0-rc.99", `gezik.old` and `update/0.1.0-rc.99/` are gone.
311. **AppImage.** Build the AppImage of the first binary too (`appimage.sh … 0.1.0-rc.2 ~/old`), start it with the same variables: the note comes, closing replaces the `.AppImage` file itself (`$APPIMAGE`, not the mounted binary): `ls -l` shows the new size and `-rwxr-xr-x`; the next start is the new version and says "Updated to". With a `gezik-portable` file beside it, the download goes to `gezik-data/update/`.
312. **Restart now.** Back to the old binary; click **Restart now** on the note: the window closes, the new version opens with the same tabs, and no second process waits behind it (`pgrep -a gezik` shows one). With the tray icon on, closing the window only hides it: nothing is installed until Quit in the tray menu.
313. **Not writable.** `sudo cp ~/old/gezik /usr/local/bin/gezik` and start `/usr/local/bin/gezik` with the feed: only "Gezik 0.1.0-rc.99 is out · Download" (Download opens the release page in the browser), nothing under `update/`. Same for the AppImage in a root-owned folder (`/opt/gezik/`).
314. **Two Gezik processes.** `[system] single-instance = false`, two windows of the old binary with the update ready: close one, then the other. Each close installs or finds it done; the file is the new version once, and the next start says "Updated to" once. A broken package (one byte changed after `SHA256SUMS.txt` was written) gives no ready note and the terminal says "does not match its SHA-256".
315. **The first real update.** Once rc.3 (the first release with the updater) is in use as a tarball and as an AppImage, and a newer release is published: within a day of starting Gezik (or at once with the palette's Check for Updates) the ready note shows, closing installs it, the next start is the new version. Without `curl` and `wget` the check fails quietly (Check for Updates says why).
